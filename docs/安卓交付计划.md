### 1.2 旧协议为什么不能直接用

| 旧协议写的 | 当前实际 |
|---|---|
| rSO₂ 由 **MBLL + 固定基线假设**（HbT=80 µM、rSO₂=65%）推出 | SRS **真绝对值**，不需要假设基线 |
| `thi` = 固定基线凑出的伪绝对量 | `thi` 有两种口径（µM 指数 / 基线=1.00 比值），都从 SRS 来 |
| 带 `cyt` 字段 | **两波长解不出**，需 ≥4 波长且噪声降 11 倍 |
| 贴肤判据用 `S1_D2` 短距、`810nm/700nm` | 当前硬件无短距、无 700nm；在用 670/770，ρ=3/4 cm |
| 基线 30~60 s 固定窗 | `BaselineManager`：攒够 20 点即设（~59 s），可抓取/手填 |
| 单位 `M`（摩尔） | 现在统一 µM |

**结论：协议要重写，不是改几个字段。** 旧文档保留作参考与历史。

### 1.3 移植成本：比想象的小

当前两波长配置下，解码器需要的**全部常数**就这些：

```
波长        670 / 770 nm
源探距离    3.0 / 4.0 cm
消光系数 ε  HbO 427.0 / 701.0      HbR 3043.0 / 1425.0     ← 4 个数
μs′(800)    10.83        谱指数 b = 0.932
增益修正 G  −0.07502105248371797, −0.08157614885859565
k / b       1.0 / 0.0    ← **未标定**，见 3.1
```

依赖情况：

| 模块 | 行数 | 外部依赖 | 移植难度 |
|---|---|---|---|
| `protocol.py` 帧解析 | 351 | **无** | 低（26 字节定长帧 + 校验和） |
| `darksub.py` 插值扣暗 | 129 | **无** | 低 |
| `robust.py` MAD 聚合 | 93 | numpy（只用中位数/均值） | 低 |
| `srs.py` 反演 + 基线 + AUC | 1028 | numpy（+scipy 仅在默认关闭的自解散射分支） | **中**，但当前配置只走其中一条窄路 |
| `mbll_core.hemoglobin_extinctions` | 134 | **pandas**（读 125 行 CSV） | **可删** —— 两波长只用上面那 4 个数 |

**当前配置下的实际运算**：2 点直线斜率 → `μeff = ln10·斜率 − 2/ρ̄` → `μa = μeff²/(3μs′)`
→ 2×2 线性方程组解 HbO/HbR → TOI = 100·HbO/(HbO+HbR)。
**没有矩阵分解、没有滤波、没有迭代**，纯算术，Kotlin/Java 直写约 300 行。

## 二、必须先定的一件事：解码器跑在哪

这决定后面全部工作，**我不替你定**。

| | A. 安卓本机解码 | B. PC 解码（沿用 TCP） | C. 安卓解码 + PC 旁路 |
|---|---|---|---|
| 数据流 | 串口 → 安卓全链路 → 显示 | 串口 → 安卓转发 → PC 算 → 回传 | 安卓算并显示，同时把原始帧发 PC 存档/复核 |
| 现场要不要带电脑 | **不要** | 要 | 不要（PC 可选） |
| 明天能否完成 | 协议+参考实现可以；**安卓侧代码我测不了** | **可以** | 协议可以 |
| 符合「给安卓一个完整解码器包」 | ✅ | ❌ | ✅ |
| 主要风险 | 两份实现要逐点对齐 | 现场依赖 PC、网络 | 工作量最大 |

**我的建议：A，但本周先按 C 过渡。** 理由：安卓独立解码是最终形态；而 C 能让安卓算的结果与 PC 算的**逐点对账**，不对齐就立刻暴露——这正是 `selftest t16` 当初验 MBLL 用的办法（界面数必须等于命令行数）。

## 三、无论选哪个，都要先解决的两件事

### 3.1 ⚠️ k/b 未标定 —— TOI 现在不是血氧绝对值

`标定_v5` 里 `k=1.0, b=0.0`，界面上一直挂着「**不是绝对血氧值，只看趋势**」。

**交付给安卓前必须明确**：这一版给出的 TOI 是**未标定的趋势量**。
协议里要有字段如实标出（见 4.3 `calibrated`），安卓界面也要显示，
否则现场会被当成可信血氧读数用。

这需要**合格的动脉阻断实验**（悬而未决第一优先）。不是明天能做完的事。

### 3.2 两份实现怎么保证一致

**做一组黄金测试向量**：从归档里挑若干段，记下每一步的输入输出，
安卓实现必须逐点复现。这是整个交付里最值钱的东西 ——
没有它，两边算得不一样时无从查起。

建议格式：`docs/安卓交付/golden/*.json`，每份含
原始帧（hex）→ 扣暗后 → 聚合后 → μa → TOI → 派生量。

## 四、接口协议要定什么

### 4.1 分层

```
L0  串口 26 字节帧      —— 已有，不动（protocol.py 第 1~35 行有完整表）
L1  解码器输入           —— 扣暗后的光强 (n_wl × n_rho) + 时刻
L2  解码器输出           —— TOI / THI / 派生量 / 质量标志
L3  安卓 ↔ PC（若选 B/C）—— JSON over TCP
```

**L2 是核心**。即便选 A（安卓本机），也要把 L2 定成明确的数据结构，
因为它就是「解码器包」的对外接口。

### 4.2 L2 输出（建议）

每个反演点一条：

| 字段 | 类型 | 说明 |
|---|---|---|
| `t` | float | 数据时刻（秒，相对本次会话第一帧） |
| `n_cycles` | int | 本点平均了几个扫描周期 |
| `toi` | float\|null | %，k/b 修正后。无效为 null |
| `thi_index` | float\|null | µM，k·tHb，**不依赖基线** |
| `mua` | float[2] | 各波长 μa（cm⁻¹），调试用 |
| `baseline` | object\|null | `{t, toi, thb, source, unstable, low_signal}` |
| `d_hbo`/`d_hbr`/`d_thb` | float\|null | µM，相对基线 |
| `thi_ratio`/`d_thi` | float\|null | 基线 = 1.00 |
| `d_toi`/`d_toi_rel` | float\|null | %O₂ / % |
| `auc_min`/`auc_below_s` | float | %·min / 秒 |
| `flags` | string[] | 物理判据异常 |
| `calibrated` | bool | **k/b 是否已标定**（见 3.1） |

### 4.3 要定的开关与命令（安卓 → 解码器）

`capture_baseline` / `set_baseline_toi(x)` / `reset_auc` / `set_avg(n)` / `mark_event(label)`

语义照搬 `BaselineManager`，**不要在安卓侧另写一套判断逻辑** ——
那是这轮改版特意把状态机放进逻辑层的原因。
