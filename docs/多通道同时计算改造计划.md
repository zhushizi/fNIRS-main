# 多通道同时计算改造计划

> 目标：通道 1 与通道 2 同时反演、同时出 TOI，未来可扩到通道 3/4；
> 每通道独立开关、独立光强。
>
> 本文只是计划，**未改任何代码**。写于 2026-10-29。

---

## 0　一句话结论

**能做，而且不需要改协议层。** 阻塞不在"能不能"，在三件事上：
① 这是对 online.py / acquire.py 的**结构性重构**，与「不要改变原有代码结构」的
长期约束直接冲突，需要你先定；② ch2 现在的硬件出不了有效值；
③ 每通道要各自一份标定，现在一份都没有。

---

## 1　必须先定的一件事：要不要动结构

`OnlineWindow.__init__`（[online.py:214](../software/srs_cal/online.py)–296）里有
**25 个属性属于"一个通道的测量态"**：

```
win / _keys / _need / _fresh / _since          滑窗与到齐判定
cycle_dark / dark_win / _darksub / _no_dark    扣暗
geom / quality / last_qflags                   标定与质量层
bl / d_hist / td_hist / ta_hist / auc_hist / last_derived   基线与派生量
t_hist / toi_hist / thi_hist / mua_hist        历史曲线
last_I / last_res / last_n / last_flags / last_rejected     最近一次反演
_q_net / _q_dark / _last_used                  质量层入参
_n_chan_ok / _n_chan_bad                       通道校验计数
```

两条路：

**甲：抽出 `ChannelPipeline` 类（推荐）**
把上面 25 个搬进一个新类，`OnlineWindow` 改持 `self.pipes: dict[int, ChannelPipeline]`。
单通道时 `pipes = {1: ...}`，行为与现在完全一致。

**乙：每个属性原地加一层通道键**
`self.win[ch][(w, r)]`、`self.toi_hist[ch]`、`self._darksub[ch]`……
不新建类，但 25 个属性的每一处读写都要加下标，online.py 里涉及约 60 处。
漏一处就是"ch2 的数据写进 ch1 的历史"，而这种错**在界面上看不出来**。

**我的判断：走甲。** 乙"看起来改动小"，但它把通道维散在 60 个下标里，
没有任何一处能集中检查。甲是一次性的结构变动，之后加通道 3/4 是
`pipes[3] = ChannelPipeline(...)` 一行。

> ⚠️ 甲违反「不要改变原有的代码结构和逻辑」。这条约束当初是为了防止
> 我借重构之名改动已验证过的算法。甲的做法是**搬运而不改写** ——
> 搬完之后单通道的 TOI 序列必须与改造前**逐点相同**（见 P1 验收）。
> 要不要这么做，请你定。

### 2.1 三个**当前就已经错**的地方（不是未来才错）

1. **周期率显示翻倍。** [online.py:928](../software/srs_cal/online.py) 和
   [acquire.py:1076](../software/srs_cal/acquire.py) 都是 `fps / FRAMES_PER_CYCLE`，
   而 `_frames_seen` 在通道过滤**之前**就自增（[acquire.py:1114](../software/srs_cal/acquire.py)）。
   双通道时设备发 15.6 帧/s，界面显示 1.3 周期/s，真值 0.656。
   *（`Take.pulsatility` 不受影响 —— 它在 `cycle_hz < 6 Hz` 时直接返回空，
   两个值都在门限下。）*

2. **`n_short_cycles` 每周期都 +1。** [protocol.py:235](../software/srs_cal/protocol.py)
   拿实测帧数与 12 比，双通道是 24。实测双通道文件里几乎每个周期都中
   （51/52、127/128、93/94、129/130），质量层会持续报假警。

3. **`rawview` 把 ch2 当异常帧。** [rawview.py:152](../software/srs_cal/rawview.py)
   `bad = (校验错 or 保留位非零 or f.channel != 1)`，还染成琥珀色。

### 2.2 一个 correctness 风险

[archive.py:245](../software/srs_cal/archive.py) 的 `replay()` **不按通道筛**，
返回全部帧。任何拿它直接喂 `DarkSubtractor` 的离线脚本，会把 ch2 的暗
（峰峰 786,447）扣到 ch1 的信号上。online/acquire 安全是因为过滤在处理之前，
离线没有这道闸。**这一条与多通道需求无关，现在就该修。**

### 2.3 一个命名陷阱

[quality.py:145](../software/srs_cal/quality.py) 的 `raw_by_channel` /
`net_by_channel` 里的 "channel" 指 **(λ, ρ) 组合**，不是采集通道
（docstring 150–151 行写明）。改造时极易误读，建议顺手改名为 `*_by_key`。

## 3　分阶段计划

原则：**协议层和离线闸先修（与界面无关），再做纯重构，再加通道，最后动界面。**
每一阶段结束时自检必须全绿，不留"下一阶段再补"的半成品。

### P0　地基（不碰界面，可独立交付）

| # | 改什么 | 为什么 |
|---|---|---|
| P0.1 | `archive.replay(path, channel=None)` 加通道筛；默认 `None` 保持现状 | 2.2 的 correctness 风险 |
| P0.2 | `FRAMES_PER_CYCLE` → `frames_per_cycle(n_active=1)`；旧常量保留为 `n_active=1` 的值 | 2.1-①②，且不破坏现有调用 |
| P0.3 | `FrameStream` 按通道各记一套 `cycle_id` / `n_short_cycles`；周期起点 = (该通道, 暗, 最近距离) | 2.1-② 的根因 |
| P0.4 | 清掉三处过期注释与提示：`EXPECTED_CHANNEL` 上方「byte10 恒为 0x01」、`cmb_chan` 的 tooltip、`build_cmd` 的「停止帧从未实测」 | 这些现在都已被实测推翻，其中 tooltip 是操作者每次点下拉都会看到的错误信息 |
| P0.5 | `rawview` 的异常判据去掉 `f.channel != 1` | 2.1-③ |

**验收**：自检 20 个用例全绿；双通道实测文件回放，`n_short_cycles` 归零，
周期率显示 0.656。

### P1　抽 `ChannelPipeline`（纯重构，行为必须不变）

新文件 `software/srs_cal/chpipe.py`：

```
class ChannelPipeline:
    def __init__(self, channel, cal, wl, rho, need): ...
    def push_net(self, key, net, t, need, nk) -> Result | None    # 原 _push_net
    def invert(self, I, n_cycles) -> Result                       # 原 _invert
    def feed_frame(self, f) -> list[Result]                        # 原 _on_frames 的循环体
    def resize(self, need): ...
    def reset(self): ...
```

`OnlineWindow` 保留 `self.pipes = {1: ChannelPipeline(...)}`，界面照旧只画 pipes[1]。

**验收（这一条是整个计划的关键）**：
取 3 份单通道实测归档回放，改造前后 `toi_hist` / `thi_hist` / `d_hist` / `auc_hist`
**逐点逐位相同**。不是"接近"，是相同 —— 纯搬运就该如此，不同即说明搬错了。
自检新增 t21 做这件事（把两版的输出各存一份 npz 比对）。

### P2　分发（让第二条流水线真正跑起来）

- `_on_frames` 的 `if f.channel != want: continue` 换成
  `pipe = self.pipes.get(f.channel)` → `if pipe is None: continue`
- **活跃通道从回传推断**，不从下发推断 —— 延续现有的"以回传为准"原则：
  见到新通道号就建一条流水线，连续 N 秒不见就标为"已停"
- 饥饿提示要能区分"这个通道关了"和"这个通道坏了"

**验收**：双通道实测文件回放，两条流水线各自出 TOI；ch1 的序列与
只喂 ch1 时**相同**（证明 ch2 的数据没漏进 ch1）。

### P3　指令层（每通道独立开关 + 光强）

`protocol.py` **不用改** —— `build_cmd(run, gear, channel)` 已经够。

界面改成一个小表格，每通道一行：

```
通道  开关   光强   回传状态
 1    [✓]   [255]  ● 0.66 周期/s
 2    [✓]   [255]  ● 0.66 周期/s
 3    [ ]   [ 15]  ○ 未见帧
 4    [ ]   [ 15]  ○ 未见帧
```

- 开 = `build_cmd(True, gear, ch)`，关 = `build_cmd(False, 0, ch)`
- 现有的「启动通道2」「关闭通道一」两个固定按钮**保留** ——
  它们是逐字节固定的协议测试帧，不是便捷操作，不该被表格取代

**验收**：自检逐字节核对四个通道的开/关/改档位共 8 条帧；
实测在体模上验"关 ch1 后 ch2 继续、再开 ch1 恢复"。

### P4　界面显示

| 控件 | 做法 |
|---|---|
| TOI 图 | 每通道一条曲线，颜色区分 —— **这是左右对比的主图，必须叠加** |
| 其余 5 张图（tHb/Δc/ΔTHI·ΔTOI/AUC/μa） | 只画"当前查看通道"，顶上加通道下拉 |
| 读数格子 | TOI 一格一通道；其余跟随"当前查看通道" |
| 事件标记 | 全局一条竖线，画在所有图上 |
| 基线 / AUC | 一次操作、各通道各抓各算（见疑问 Q5） |

为什么其余图不叠加：4 通道 × Δc 的 3 条 = 12 条曲线，没法读。
TOI 是唯一需要跨通道同屏对比的量。

### P5　acquire 多通道

- 一次「采集」产出 **N 个 Take**（每通道一个），复用已有的 `Take.channel`
- xlsx 不用改结构：明细已有 `channel` 列，汇总已有「通道」列
- `_cycle_hz` 改用 P0.2 的函数

### P6　自检

新增：t21 重构等价性（P1 的验收）、t22 多通道分发隔离、t23 四通道指令帧逐字节、
t24 每通道独立档位。

## 4　疑问清单

### 阻塞的（这三条不定，做了也不能用）

**Q1　要不要动结构？** 见 §1。甲（抽类）还是乙（加下标）。
我推荐甲，但它违反「不改结构」的约束，必须你点头。

**Q2　ch2 的硬件什么时候修？**
实测 ch2 的 770 的 I3/I4 = 1.42~1.69，低于几何下限 (4/3)² = 1.778，μeff 必为负；
670 净值 100% 为负，三份文件复现到 0.6%。
代码可以先做（改造是机械的，与 ch2 好坏无关），但**验收只能用模拟器 +
单通道回归**，不能拿 ch2 的真数据当"通过"。

**Q3　每通道的标定谁来采？**
`G(λ)` / `k` / `b` 是 ch1 这套探头在体模上标的。换通道 = 换探头 = 换光学套件，
标定不跨套件转移。没有 ch2 的标定，ch2 的 TOI **绝对值无意义**（相对变化仍可看）。
这要上体模采一轮，不是代码能解决的。

### 不阻塞但要问厂家的

**Q4　byte6 = 0x03 是"ch1+ch2"还是"通道 3"？**
文档写「0x00 全部 / 0x01 一通道 / 0x02 二通道…累加依次」。
"累加"字面像位或，"依次"像序号递增。
*好消息：这条不阻塞。* 实测已知 byte6=0x02 会让 ch2 加入而 ch1 保留，
byte4=0x00+byte6=0x01 只关 ch1 —— 所以"逐个开关"已经可行，
Q4 只影响"能否一次开多个"和 0x03/0x04 的含义。

**Q5　4 通道时帧率怎么走？**
实测 2 通道时设备把帧率从 7.9 翻到 15.6 帧/s，ch1 的周期率保持 0.656/s 不变
（即不是分时间，是真翻倍）。4 通道会翻到 31 帧/s 吗？
按 26 字节/帧算也只有约 8 kbps，串口不是瓶颈，但要实测确认周期率不掉。
若周期率掉一半，4 通道的时间分辨率就减半，这会影响临床可用性。

**Q6　电气串扰到 4 通道会多大？**
实测开 ch2 让 ch1 的稳健快噪声涨 5.3~5.9 倍（六个时隙一致，**暗时隙涨得
一样多** → 加性电气干扰，非光学）。体模上可忽略（TOI σ 0.047→0.118），
但加性噪声约 5,100 计数是固定的，在体弱信号下占比会放大。
4 通道若线性叠加可能到 10 倍以上。**这是硬件问题，必须向厂家提。**

### 我自己定了的（不用问）

- **Q7　基线/事件/AUC 的作用域**：事件标记全局（操作者按的）；
  基线与 AUC 按"一次操作、各通道各存各算"。理由：抓基线是一个时刻的动作，
  但每通道的基线值必然不同。
- **Q8　acquire 一次采集的产出**：N 个 Take，不是一个 Take 带 N 份数据。
  `Take.channel` 和 xlsx 的通道列都已存在，这样改动最小。

## 5　不做什么

- 不在 P1 之前碰界面。重构和功能混在一起改，出了问题分不清是哪边的。
- 不改 `parse_frame` / `checksum` / `build_frame` 的逻辑。
- 不动 `config.py`（长期约定）。
- 不"顺手"改 `BRIGHTNESS_MAX`（0xFF vs 厂家文档的 0x64）——
  实测档位 255 的读数约为 100 的 2 倍，设备并未在 100 截断，这条要单独定。
- 不给 ch2 的坏数据加"修复"逻辑。已验证不可救：标签错位假设被实测否决
  （4cm 最小值交替落在 670:39/770:25，相邻周期摆动 7.5 倍）。

## 6　顺序建议

```
P0（地基，独立交付，现在就该做）
 └─ Q1 定了 ──> P1（纯重构 + 等价性验收）
                 └─ P2（分发）── P3（指令）── P4（界面）── P5（acquire）── P6（自检）

并行、不依赖代码：
 Q2 ch2 硬件诊断   ← 最该先动的，它决定多通道有没有意义
 Q3 ch2 标定采集   ← 硬件好了才能做
 Q4~Q6 向厂家提问
```
