### 20:40　「查看」下拉改成纯视角切换（用户报的 UI 问题）

- **角色**：回退 / 修正（用户发现：在通道 1 等曲线画满 → 点开通道 2 看 →
  切回通道 1，两边都重新开始采集和画图）
- **改了什么**：
  - `online.py:_on_channel`：**不再** `_send_brightness()`，因而不再清屏。
    只换 `_view_ch`、同步档位框（blockSignals）、立刻 `_refresh()`
  - `online.py:_send_cmd`：清屏条件从"一律清"改成**只有光强真的变了才清**；
    启停帧改为 `pipe.break_line()`（留历史、插一道 NaN 断口）
  - `chpipe.py`：新增 `break_line()`；`n_frames` 移出 `_init_state`，
    **不随清屏归零**
  - `online.py:_chan_counts()`：界面改用**各流水线自己的** `n_frames`
    判「这个通道有没有数据」，不再用窗口级累计
  - `online.py:_refresh_chan_label`：删掉「另有 N 帧属其他通道」那条
  - TOI / μa 曲线加 `connect="finite"`，断口才画得出来
- **为什么**：多通道同时计算的全部意义就是数据已经在后台算着，
  切过去应该立刻就有。改造前「查看」下拉还走着单通道年代那条路
  （换通道 = 换探头 = 必须清屏），把同时计算的收益整个抵消了
- **依据**：实测
- **怎么确信的**：
  - 根因不是"清屏写错了"，而是**一个控件管了两件事**。单通道时
    "看哪个"和"控制哪个"本来就是同一件事，多通道之后分叉了而我没拆。
    拆法：开/关归复选框，光强归档位框，下拉只决定"画谁"
  - 为什么停通道时不清屏而是插断口：停之前那段数据本身没问题，
    恰恰常常是操作者想留着看的那一段 —— 他停它就是因为看到了什么。
    清掉等于把停它的理由也扔了。但两段之间有空档，直连会画出一条
    横跨空档的假斜线，所以插 NaN + `connect="finite"`
  - `n_frames` 为什么不能随清屏归零：界面拿它回答「这个通道到底发不发帧」
    （链路事实），不是「屏上有几个点」。归零后改一次档位就会把
    "刚清掉"误报成"该通道无数据" —— 实测到了，⑥ 那一步
  - 删「另有 N 帧属其他通道」的理由：多通道同采时 `other` 恒大于 0，
    这条会把下面的**标定警告永远挡住**。而标定警告是真要紧的那条
    （非 1 号通道的 TOI 是拿 1 号的 G(λ) 算的，绝对值不可信）。
    这是自检逼出来的 —— 判据过不去，查下去发现是优先级设计错了，
    不是断言写错了
- **验证**：自检 t21 新增 6 条（来回切不清屏 / 切视角不下发 /
  停通道插断口 / 不重复插 / 改档位仍清屏）；真实归档实测：

  手敲串口助手不如在本来就连着设备的两个程序里各挂一个按钮
- **依据**：上游确认（厂家协议文档的数据位定义）+ 用户指定的字节串
- **怎么确信的**：**没走「改控件 → 触发下发」那条路**。那条路会重新造帧，
  而 `build_brightness` 的 byte4 恒为启动 —— 关闭帧会在发出前变回启动帧，
  按钮看着能按、实际做的是反的事。所以固定帧必须原样送、控件事后同步，
  且同步时要 `blockSignals`，否则 `setValue/setCurrentIndex` 会再触发一次下发
  把刚发的帧覆盖掉。两条都有断言守着（「不二次下发」「末帧 byte4=00」）。
- **验证**：t19 两项、t20 五项，逐字节对着**用户给的那串**验，
  不是对着我们自己造的

## 推翻 / 否决 / 作废

今天拿到厂家的通讯协议文档（截图），指令帧的三条判断同时被推翻。
**三条都是我此前写进 `protocol.py` 注释并当事实用的。**

| 字节 | 我原来写的 | 文档写的 |
|---|---|---|
| byte4 | 「固定 0x01，含义未明；早先注释成启停是猜测，**已证伪**」 | **启/停**：0x00 停止 / 0x01 启动 |
| byte5 | 「0x00~0x96(150)」，代码放到 0xFF(255) | **强度 0~100**（0x00~0x64） |
| byte6 | 「是通道号**没有厂家文档**，按字节位置推的」 | **通道选择**：00 全部 / 01 一通道 / 02 二通道… |

### ✗ 作废：「协议里没有关闭指令，只能用档位 0 凑合」

今天上午我据此给了用户一条「档位 0」当关闭用，并说「0x00 是最暗还是关闭待确认」。
文档里 byte4 就是启停位，**停止指令一直存在**。

> 教训：**「我反推的结论」和「我证伪的结论」都不是事实。**
> 「已证伪」三个字当时让我对 byte4 彻底停止了怀疑 —— 比没结论更糟。
> 证伪用的证据是「设备上电即发数据、不发启动也有数」，
> 这只能说明**启动不是必需的**，推不出「这个字节不是启停位」。

### ✗ 推翻：档位上限

10-27 的两份信号线对比采集都用了档位 **255**，是文档上限 100 的 2.55 倍。
设备对越界值如何处理（饱和 / 取模 / 忽略）未知。
两份之间仍可比（同为 255），但那组的绝对光强不能与文档范围内的采集比。

### ✗ 不利的答案：档位调的是**电流**

文档写「强度（光源电流可调）」。`protocol.py:325` 标着「须问厂家档位是调电流
还是 PWM 占空比」—— 现在有答案了，而且是不利的那个：LED 峰值波长随驱动电流
漂移，调电流比调 PWM 漂得多。

**后果**：「不同体模块用不同档位迁就动态范围不影响 G(λ)」这个前提更站不住了。
验证办法早已写在 `build_brightness` 的注释里（同一块体模、探头不动，
两三个档位各采一次比 G(λ)，波长相关差异应 < 0.005），该补上。

### ⚠ 文档自身的一处不一致

文档示例帧 `55 AA 1A 01` + 21 个 `00` + `1E`，长度 26 正确，
但按它自己定义的「从帧长度字节到最后一个帧数据字节累加取低字节」应为 **`1B`**，差 3。
（放大数过零的个数，确是 21 个。）

校验规则本身没问题 —— 厂家 10-10 的另一个样例 `55AA 1A 01 01 00 01 …1D`
与实机 7 帧全部对上。**是这个示例写错了，别照抄。**

### ✗ 推翻：「byte10 恒为 0x01，切换无法从回传证实」

`protocol.py` 里这条写了两处、界面 tooltip 上一处，依据是「全部 46,572 帧
归档里 byte10 从没出现过别的值」。今天实测**开通道 2 后 byte10 确实回 0x02**。

10-28 那次"切换无效"的真因是**当时没有 2 号通道的硬件**，不是指令不对。

> 教训：「N 帧里没出现过」是**该条件下**的观察，不是协议事实。
> 我把它写成了后者，还据此在界面上告诉操作者"切换生效了没有无法证实"——
> 那是**操作者每次点下拉都会看到的错误信息**，比代码注释里的错更贵。

### ✗ 推翻：「五路 LED 随档位等比例变化（未验证）」

实测（同体模、探头不动，档位 255 与 100 各采一次）：十路的 100/255 比值在
**0.384~0.507，极差 28.4%** —— 等比例**不成立**。

但它在 SRS 里抵消：同一波长的两个距离上因子几乎相同（670: 0.507/0.505；
770: 0.414/0.414），I3/I4 基本不动，TOI 83.91 → 83.67，只差 0.24 点。

> 结论不变（改档位对 SRS 安全），但**理由换了**：
> 不是"等比例"，而是"同一波长的两个距离同比例"。
> 原来那个理由是错的，只是恰好得出了对的结论 —— 这种最危险。

### ⚠ 自检里试出来的一个"看似合理其实无效"的造数方法

t21 要造"另一个通道"来验没有串台，第一版把 ch2 整体乘 0.55。
**TOI 一点没变** —— 整体缩放不改 I3/I4，这正是"改档位对 SRS 安全"的原因。
第二版只压 4cm 但两个波长一起压，TOI 只差 **0.30 点**（两路 μeff 同向平移）。
最后只压 **670 的 4cm**，才真正改动 μeff 之比，TOI 差 **54 点**。

> 教训：**造反例时要先问"这个改动会不会被待测量本身消掉"。**
> 前两版的判据都能"通过"，但通过了什么都没验到。

## 踩的坑（我自己的）

### 一个控件管了两件事

「查看」下拉在单通道时代同时意味着"看哪个"和"控制哪个"—— 那时两者本来
就是同一件事。改成多通道同时计算之后它们分叉了，而我**没拆**，于是
"看一眼别的通道"会当成"换探头"把曲线清掉。

用户一上手就撞到了；而我的自检里有一条
「换通道后清屏（换探头 = 换光学套件，旧曲线与基线作废）」
**把这个错误行为锁住了** —— 那条判据是单通道时代写的，改造时我只顾着
让它继续通过，没问它现在还成不成立。

> 教训：**改了语义之后，先去看哪些判据正在守着旧语义。**
> 自检全绿不代表行为对，只代表行为和判据一致 —— 两边一起错时它最沉默。

### `clicked` 多塞一个 `False` 实参

`_reset` 加了 `channels` 形参后，`btn_reset.clicked.connect(self._reset)`
会把 `checked=False` 当成 `channels` 传进去 → `for c in False` 抛 TypeError。
自检没抓到，因为 t19 是直接调 `win._reset()`，没走信号。

已改成 `connect(lambda: self._reset())`，并补了一条**点按钮**（而不是调方法）
的判据。

> 教训：**给已连到信号上的槽函数加形参时，先看那个信号带不带参数。**
> 并且：测一个按钮要 `.click()`，不是调它的槽 —— 否则测不到接线。

### 自检里 `setChecked(True)` 是空操作

t20 新加的开关判据报「一帧没发」—— 因为前面的下发已经把 3 号的复选框
带成勾选了，再 `setChecked(True)` 不触发 `toggled`。

> 教训：**断言之前先把起始状态显式摆正**，别假设它还是构造时那个值。

### 造测试帧时 `raw=b""`

t20 第一版照着 t19 的写法造 `Frame(..., raw=b"")`。t19 能过是因为 online
不读 raw；acquire 的「终端打印」会对每帧算校验，当场 `IndexError`。
改为用 `build_frame` 造真字节，顺带把打印路径也覆盖到了。

> 教训：**照抄另一个模块的测试夹具前，先看被测模块多读了哪些字段。**

### 在离屏自检里弹模态框 → 段错误

`start_capture` 的拦截我写成了 `QtWidgets.QMessageBox.warning`，
自检跑到那里直接 segfault（退出码 139），而且因为 stdout 有缓冲，
崩溃点显示在 t15，查了一轮才定位到 t20。

**而项目本来就有这条惯例**：`_banner` 的注释第一句就是
「非阻塞的判定提示。**替代模态框**」。我没照着做，是又加了一个模态框。
改用 `_banner` 之后既不崩、也能断言文案。

> 教训一：**段错误后先用 `-u` 重跑**，缓冲会把崩溃点显示在几百行之前。
> 教训二：加一个提示之前，先看同文件里现有的提示是怎么做的。

### 对照串拆成两行写，多打了一个字节

t20 里把用户给的 26 字节拆成两段字符串拼接，第一段多写了一对 `00` ——
27 字节。断言当场红了，而同一组字节在 t19 里（单行写）是通过的，
两边对比才看出是**对照串**错了，不是被测代码错了。

已补一条断言 `len(WANT_CH2) == 26`：**对照值自己也要被验**。

> 教训：**逐字节的对照串不要跨行拼接。** 一行写不下就换种写法
> （`bytes.fromhex` 本来就允许空格分组），别让人去数零。

## 悬而未决

| 项 | 状态 |
|---|---|
| `BRIGHTNESS_MAX` 要不要从 0xFF 降到 0x64 | **未改，等用户定**。实测 255 档约为 100 档的 2 倍，设备**没有**在 100 截断，所以也不能照文档直接降 |
| 通道「累加依次」是位掩码还是顺序编号 | **未定，要问厂家**。位掩码读法下 `0x03` = 一+二通道同开，顺序编号读法下是三通道。*不阻塞逐个开关* —— 逐个下发 01/02 累加、byte4=00 按通道停，两条都已实测可行 |
| 通道 `0x00`（全部开启）发不出去 | 代码 clamp 在 `CHANNEL_MIN=1`。要支持得放开下界，但 0x00 的语义先要厂家确认 |
| 帧标识 `0x03` 应答帧 / `0x04` 按键帧被丢弃 | `parse_frame` 只收 `0x02`，其余计进 `n_dropped`。若下位机已在上发按键帧，我们既收不到、丢帧计数还虚高 |
| 模拟器不支持多通道 | `build_frame` 的通道走默认 1，选通道 2~4 在模拟器下一帧都收不到。这与真机表现一致，不算 bug，但排练不了多通道 |
| **四个通道共用 1 号的标定** | 用户 2026-10-29 决定，先不等每通道各标一份。**后果：非 1 号通道的 TOI 绝对值不可信**，只能看相对变化。界面上有提示（`_refresh_chan_label`），但这条必须在交付前解决 |
| **ch2 硬件未修** | 用户决定先按"正常"处理。实测 ch2 的 770 的 I3/I4 = 1.42~1.69，低于几何下限 (4/3)²=1.778，μeff 必为负；670 净值 100% 为负。代码里它会**诚实地报 flags 而不出值**，不会画假曲线 |
| ch2 对 ch1 的电气干扰 | 实测 ch1 快噪声涨 5.3~5.9 倍（暗时隙涨得一样多 → 加性电气，非光学）。体模上 TOI σ 0.047→0.118 可忽略，但加性噪声约 5,100 计数是**固定的**，在体弱信号下会放大。4 通道会多大未知，**要向厂家提** |
| 4 通道时周期率会不会掉 | 2 通道实测帧率 7.9→15.6 翻倍、每通道周期率不变（0.656）。4 通道按 26 字节算约 8 kbps，串口不是瓶颈，但要实测确认 |
| `acquire` 一次采集仍只收一个通道 | P5 未做。标定本来就是一次标一套探头，且现在共用标定，暂无必要。要做就是"一次采集产出 N 个 Take"，`Take.channel` 和 xlsx 的通道列都已就位 |
| **2026-10-28 的变更记录缺失** | 当天的通道选择、回传校验、信号线耦合诊断都已提交（`74030b7`/`853d32b`），但没有记录文件 |
| 档位改电流 → 需验证 G(λ) 是否随档位变 | 见上。办法已写在 `build_brightness` 注释里，未做 |
